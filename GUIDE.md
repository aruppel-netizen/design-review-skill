# Скилл «Дизайн-ревью» — гайд

Скилл для Claude, который проверяет сборку разработчика по эталону. Эталон — это макеты в Figma и, если в Figma чего-то нет, прототип или спецификация из репозитория. Сборка может быть стендом, локальной сборкой разработчика, веткой, скринами или видео. Скилл находит отклонения, сортирует их по критичности и оформляет замечания в шаблон ревью в Figma или в документ.

Запускать его может и дизайнер на приёмке, и разработчик для самопроверки до передачи на ревью.

**Идея:** механическую сверку делает Claude, а дизайнеру остаётся то, что требует суждения: сценарии, логика, восприятие, потеря данных. Из 16 критериев регламента скилл полностью закрывает 13, в том числе все «Значимые» и «Незначительные».

> ### Коротко
> - **Что делает:** сверяет сборку с макетом в Figma и прототипом из репо, находит расхождения в отступах, шрифтах, радиусах, токенах и состояниях и собирает отчёт.
> - **Где работает:** Claude (claude.ai, Desktop, Code), Codex, ChatGPT (в ChatGPT только по скринам).
> - **Как поставить:** включить по [ссылке в claude.ai](https://claude.ai/customize/skills/id/plugin_01FDUzPqqPJgE1hGiBgsDXaN) или запустить Claude Code / Codex из репозитория проекта. Подключить Figma и браузер.
> - **Как запустить:** «Сделай дизайн-ревью» + ссылка на **фрейм** Figma (`node-id`) + сборка (стенд, `localhost`, скрины) + **что не вошло** в итерацию.
> - **Что получите:** 🔴 Критичные · 🟠 Значимые · ⚪ Незначительные · ❓ Уточнить, а также что проверено и что нет, и типовые ошибки.
> - **Чекап компонентов ДС:** в каждом ревью скилл проверяет, собран ли экран из компонентов и токенов дизайн-системы с нужными вариантами или это локальные копии и хардкод.
> - **Кому:** дизайнеру для приёмки сборки, разработчику для самопроверки до ревью. Критичные и Значимые чинятся до релиза.
> - **Повторное ревью:** приложите прошлый отчёт, и скилл покажет, что исправлено, что осталось и что появилось нового. Максимум две итерации.

## Где работает

Скилл написан в открытом формате **Agent Skills** (папка с `SKILL.md`). Этот формат понимают Claude, OpenAI Codex и ChatGPT, поэтому скилл один и тот же для всех трёх сред. Отличаются только инструменты, через которые он ходит в Figma и в браузер. Таблица соответствия лежит в `design-review/references/tools.md`, и скилл читает её сам.

| Среда | Figma | Живой стенд | Шаблон в Figma | Режим |
|---|---|---|---|---|
| **Claude Code** | ✅ Figma MCP | ✅ Claude in Chrome или Playwright MCP | ✅ | полный |
| **Claude Desktop / claude.ai** | ✅ коннектор Figma | ✅ Claude in Chrome | ✅ | полный |
| **OpenAI Codex** (CLI / IDE / app) | ✅ Figma MCP | ✅ Playwright или Chrome DevTools MCP | ✅ если есть `use_figma` | полный |
| **ChatGPT** | ⚠️ коннектор Figma, если подключён | ❌ обычно только скрины/видео | ❌ | по скринам, результат документом |

Если какой-то возможности нет, скилл скажет об этом в начале и перейдёт на запасной вариант: скрины вместо стенда, документ вместо шаблона в Figma.

## Установка

### Claude Code

```bash
./install.sh claude
```
Скрипт копирует скилл в `~/.claude/skills/design-review/`. Чтобы скилл появился у всей команды, выполните `./install.sh repo /путь/к/репо`: он положит скилл в `.claude/skills/` и `.agents/skills/` этого репозитория.

Подключения: Figma MCP (плагин Figma или `claude mcp add`) и браузер, то есть расширение **Claude in Chrome** или Playwright MCP.

### Claude Desktop / claude.ai

Settings → Capabilities → Skills → **Upload skill** → `design-review.skill`. Подключите коннектор Figma и расширение Claude in Chrome.

### OpenAI Codex

1. Установите скилл:
   ```bash
   ./install.sh codex
   ```
   Скилл ляжет в `~/.agents/skills/design-review/`. Для команды кладите его в `.agents/skills/` в репозитории (`./install.sh repo …`). В старых версиях Codex скиллы читались из `~/.codex/skills/`. Если скилл не подхватился, скопируйте его туда.
2. Подключите MCP. Скопируйте блоки из `codex/config.toml.example` в `~/.codex/config.toml`:
   - `figma` — удалённый сервер `https://mcp.figma.com/mcp`. Авторизация: `codex mcp login figma`.
   - браузер: **Playwright MCP** (свой браузер) или **Chrome DevTools MCP** (ваш Chrome). Нужен один из двух.
3. Перезапустите Codex. Проверить, что подхватилось, можно командами `/skills` и `/mcp`.

Запуск такой же, как в Claude: «сделай дизайн-ревью…». Можно и явно: `$design-review`.

### ChatGPT

1. Skills → **Create** → **Upload from your computer** → `design-review.zip`. Дождитесь, пока закончится проверка.
2. Если в рабочем пространстве загрузка скиллов выключена, попросите админа включить **Enable skill uploading**.
3. По возможности подключите приложение (коннектор) Figma.
4. В чат прикладывайте скрины или видео сборки и ссылку на макет. Результат придёт документом.

**Ограничение ChatGPT:** выполнять JS на стенде он не может, поэтому отступы и типографику скилл оценивает по картинке и помечает как «низкая уверенность». Для точного ревью используйте Claude или Codex со стендом.

## Как запустить

Скилл запускается сам по фразам вроде «дизайн-ревью», «сверь стейдж с Figma», «проверь, соответствует ли сборка макету», «собери замечания для разработчика», «сверь с прототипом», «проверь мою сборку перед ревью», «повторное ревью».

Сразу передайте три вещи:

1. **Эталон:** ссылку на фрейм в Figma с `node-id` (не на файл целиком) и/или эталон в репозитории (подробнее ниже).
2. **Сборку** в любом из вариантов:
   | Вариант | Как скилл с ней работает |
   |---|---|
   | URL стенда или превью | открывает в браузере и снимает стили из DOM. Самый точный вариант |
   | локальная сборка разработчика (`localhost:…`) | то же самое, но браузер должен быть на той же машине, где запущена сборка |
   | ветка или PR | просит превью-стенд. Если его нет, запускает по README во временной папке, код не трогает |
   | скрины или видео | сравнивает по картинке, точность ниже |
3. **Что осознанно не вошло в релиз.** Без этого списка будут ложные замечания. Пункты «под вопросом» скилл вынесет в отдельный блок «Уточнить».

Можно добавить: тестовые учётки, нужные вьюпорты, браузеры, режим (первичное или повторное ревью), кто запускает (дизайнер или разработчик), формат результата (Figma или документ).

**Для чекапа компонентов ДС** дайте скиллу код сборки: ссылку на ветку или PR, либо запускайте его из папки проекта. Тогда он проверит импорты, пропсы и хардкод в самом коде. Без кода проверка пойдёт только по DOM, и хардкод будет отмечен как «похоже на хардкод». Сам чекап делается всегда, отдельно просить не нужно.

### Эталон из репозитория

Не всё есть в Figma. Выпадашки, состояния и корнер-кейсы часто живут только в прототипе. Тогда скилл берёт эталон из репозитория:
- **прототип** (HTML/JS, Storybook). Скилл клонирует репо во временную папку, запускает его (`python3 -m http.server` или как написано в README), выставляет то же состояние, что на сборке, и снимает стили тем же способом. Получается сравнение DOM с DOM, без догадок. Через `file://` прототип не открывается: не грузятся иконки и данные;
- **спецификация**: `DESIGN_FIGMA.md` со ссылками на ноды, `CORNER_CASES.md`, README;
- **токены и кит**: ожидаемые размеры и варианты компонентов, Code Connect.

Если источники расходятся, приоритет такой: фрейм Figma, затем спецификация, затем прототип. Если прототип противоречит макету, скилл выносит это в «Уточнить» и не выбирает сам. У каждого замечания указано, откуда взят эталон: из макета или из прототипа.

Клонировать и запускать скилл умеет только в Claude Code и Codex, где есть терминал. В Claude Desktop прототип запускаете вы и даёте ссылку на `localhost`. В ChatGPT нужны скрины прототипа.

### Самопроверка разработчика

Разработчик прогоняет скилл на своей сборке до того, как отдать её на ревью, и механические расхождения ловятся заранее. Правила такие:
- отчёт считается черновиком к приёмке, а не приёмкой;
- Критичные и Значимые чинятся до передачи, «Уточнить» не чинится, а приносится дизайнеру;
- если замечание кажется ложным, его не удаляют, а оставляют с комментарием. Решает дизайнер;
- в таблице «Компоненты ДС» статусы ⚠️, ❌ и 🎨 исправляются до передачи, даже если на глаз разницы нет.

В инструкцию для разработчика стоит добавить ориентиры по компонентам: какие компоненты кита и в каких вариантах должны быть на экране, и на чём уже спотыкались. Например: «чипсы — размер L, а не XS по умолчанию».

Удобно положить в репозиторий инструкцию `design-review/DEV_SELF_REVIEW.md`: как поставить скилл, ссылки на макеты и прототип, что не вошло, готовый запрос и как читать результат. Скилл читает её первой и не переспрашивает то, что там уже есть. Пример — `search-bar-web/design-review/DEV_SELF_REVIEW.md`. Скилл может и сам составить такую инструкцию по вашей просьбе.

**Пример запроса:**
> Сделай дизайн-ревью. Макет: https://figma.com/design/…?node-id=12-345. Стенд: https://stage.example.com/search. Код сборки: <ссылка на PR>. Не вошло: фильтр по метро и пустое состояние избранного. Вьюпорты 1440 и 375. Результат — шаблон в Figma.

Если чего-то не хватает, Claude спросит всё одним сообщением.

## Что происходит внутри

| Шаг | Что делает Claude | Чем |
|---|---|---|
| 0. Вход | Читает инструкцию к ревью в репо, если она есть, и одним сообщением спрашивает недостающее | — |
| 1. Эталон из Figma | Снимает дерево нод, свойства, **токены** и скриншоты фреймов | Figma MCP: `get_metadata`, `get_design_context`, `get_variable_defs`, `get_screenshot` |
| 1б. Эталон из репо | Читает спецификацию и токены, запускает прототип и снимает с него стили | терминал (`git clone`, локальный сервер) + браузер |
| 3б. Чекап компонентов ДС | Сверяет компоненты и варианты из макета с тем, что использовано в сборке и коде. Ищет хардкод вместо токенов | Figma: `get_code_connect_map`, `search_design_system`; DOM; код сборки, если есть доступ |
| 2. Сборка | Проходит по вьюпортам и состояниям, снимает computed styles, ищет битые картинки, пикселизацию, скачки лейаута, неразрывные пробелы | Браузер: открыть страницу, сменить вьюпорт, выполнить JS, снять дерево доступности. Имена инструментов в каждой среде свои, см. `references/tools.md` |
| 3. Сравнение | Три слоя: точное сравнение по токенам → визуальный дифф (только чтобы найти подозрительные зоны) → разбор этих зон | — |
| 4. Классификация | Присваивает каждому замечанию класс по регламенту | — |
| 5. Оформление | Шаблон в Figma или Markdown-документ + короткая сводка для Slack | Figma `use_figma` (через скилл `figma-use`) |

**Важно про сравнение:** Claude сравнивает токены и относительные величины, а не абсолютные пиксели, и учитывает DPR. Реальные данные вместо плейсхолдера багом не считаются.

## Чекап компонентов дизайн-системы

Этот шаг есть в каждом ревью, даже если визуально всё совпало. Скилл проверяет не только, похож ли экран на макет, но и из чего он собран.

1. **Что ожидается.** Из макета скилл выписывает компоненты библиотеки с их вариантами (`Size=L`, `State=Active`). Через Code Connect находит, какой компонент кода им соответствует.
2. **Что использовано.** В сборке скилл ищет компоненты кита по DOM: классы, `data-*`-атрибуты. Если есть доступ к коду, смотрит импорты, пропсы (`size="XS"` вместо `"L"`) и хардкод значений вместо токенов.
3. **Результат.** В отчёте появляется отдельная таблица «Компоненты ДС»:

| Статус | Значит |
|---|---|
| ✅ | компонент и вариант совпадают |
| ⚠️ | компонент тот, но вариант или пропсы другие |
| ❌ | свой, старый или скопированный компонент вместо китового |
| 🎨 | хардкод вместо токена |
| ❓ | определить не удалось: нет доступа к коду или признаков в DOM |

Если отличие видно глазами, класс ставится по обычным правилам, обычно это Критичное. Если глазами разницы не видно (локальная копия, хардкод), это Значимое: сейчас незаметно, но разъедется при следующем изменении ДС.

Заодно скилл проверяет сам макет: отвязанные (detached) инстансы и цвета вне токенов. Такие находки идут в «Уточнить» для дизайнера, а не разработчику.

Повторяющиеся ошибки в компонентах попадают в «Базу типовых ошибок». Там предлагается профилактика через Code Connect, например прописать нужный вариант по умолчанию.

## Классы критичности

| Класс | Когда чинить | Что входит |
|---|---|---|
| 🔴 **Критичные** | до релиза | сломанный сценарий, тупики, необработанные ошибки; контент, сетка или тексты не по макету; состояния контролов; битые и пиксельные картинки; **отступы с отклонением ≥ 8px или ≥ 25%**; потеря данных пользователя |
| 🟠 **Значимые** | до релиза | типографика; отображение на разных разрешениях; контраст и доступность на основном пути |
| ⚪ **Незначительные** | после релиза | размер иконок и иллюстраций; неразрывные пробелы; **отступы < 8px и < 25%**; кросс-браузерность; планшет |

Пороги по отступам указываются в шапке отчёта, их можно подстроить после первых прогонов.

Отдельно от UI идут:
- **Логика**: свой блок, с шагами воспроизведения и пометкой «сверить с QA на дубли».
- **Рефакторинг**: помечается как «отдельная задача», через ревью не протаскивается.
- **Уточнить**: расхождение есть, но неясно, входит ли оно в итерацию (пункт под вопросом, макет спорит с прототипом, нет фрейма на состояние). Класс не ставится, у блока своя колонка в счётчике.

## Что получится на выходе

**Шаблон в Figma** (по умолчанию):
- слева «как в сборке» с подсвеченными зонами, справа «как нужно»;
- пронумерованные маркеры, у каждого: что не так, ожидаемый результат, класс;
- Критичные сверху, у каждого замечания статус «Не исправлено / Исправлено»;
- в шапке: задача, дата, вьюпорты, пороги, счётчик по классам.

**Документ:** та же структура в Markdown:
- в шапке — сборка, эталон (ноды и прототип), условия проверки (браузер, DPR, ширина окна), пороги;
- счётчик «Критичные · Значимые · Незначительные · Уточнить»;
- у каждого замечания таблица «Сборка / Макет (или Прототип)» и скрины;
- таблица «Компоненты ДС» со статусами ✅ ⚠️ ❌ 🎨 ❓;
- в конце — «Проверено / Не проверено» и «В базу типовых ошибок».

Если работа идёт в репозитории, отчёт сохраняется в `design-review/<дата>/REVIEW.md`, скрины кладутся рядом (`build-*`, `figma-*`, `proto-*`). Эта папка нужна для повторного ревью. Пример — `search-bar-web/design-review/2026-11-19/`.

**Сводка для Slack:** счётчик по классам и «Уточнить», ссылка на отчёт и пометка, если мелких замечаний много.

## Матрица состояний

Claude проверяет каждое состояние, а то, что не проверено, явно отмечает в отчёте:

- **Данные:** загрузка, пусто, много, мало, длинные тексты
- **Ошибки:** валидация, системная, нет сети
- **Контролы:** hover, pressed, focus, disabled, поиск
- **Навигация:** скролл, пагинация, анимации
- **Адаптив:** ориентация, разрешения, браузеры, планшет
- **Система:** тёмная тема, крупный шрифт, safe areas, клавиатура
- **Загрузка:** скелетоны, резерв места, скачки лейаута
- **Доступность:** контраст, тап-зоны, фокус с клавиатуры

## Повторное ревью

Дайте ссылку на прошлый отчёт или шаблон. Claude сопоставит замечания по отпечатку (класс + нода + свойство + селектор, без координат) и разложит их на три группы:
- **Исправлено**: дизайнеру остаётся только подтвердить;
- **Не исправлено**: поднимается выше в списке;
- **Новое**: помечается как регрессия.

**Лимит — две итерации.** Если после второй остались Критичные, третьего круга не будет: это повод разобрать причины с командой.

**Ревью закрыто**, когда Критичные и Значимые исправлены и подтверждены, Незначительные заведены в бэклог с меткой `design-debt` и сроком, а у всех замечаний стоит финальный статус.

---

## База типовых ошибок

В конце каждого прогона Claude выводит блок «В базу типовых ошибок»: повторяющиеся замечания и способ закрыть каждое навсегда (правило линтера, правка UI-кита, токен, гайдлайн, Code Connect).

## Ограничения и советы

- **По скринам и видео точность ниже.** Отступы и типографика в таком режиме помечаются как `confidence: low` («похоже на…»). Для точного ревью нужен URL стенда.
- **Ссылка на файл без `node-id` не подойдёт**, нужен конкретный фрейм.
- **Не забывайте про «что не вошло»**: это главный источник ложных замечаний.
- Скилл старается дать **меньше, но точнее**: 5 подтверждённых замечаний лучше 30 с мусором.
- Большую часть замечаний снимает короткий walkthrough макетов с разработчиком до начала разработки.

## Как обновлять скилл (для владельца)

Источник правды — папка `skills-export/design-review/`. Правьте только её, а копии в репозиториях не трогайте: при следующей публикации они перезапишутся.

```bash
./publish.sh "что поменяли"          # архивы + коммит в репо проекта
./publish.sh --push "что поменяли"   # то же + push в gitea
```

Скрипт:
1. проверяет, что description в SKILL.md не длиннее 1024 символов;
2. пересобирает `design-review.skill` и `design-review.zip`;
3. обновляет `.claude/skills/` и `.agents/skills/` в репозитории проекта (список репозиториев задан в `REPOS` внутри скрипта) и коммитит только эти папки;
4. открывает страницу скилла в claude.ai. Новый `design-review.skill` туда загружается вручную, после чего у всех в Claude скилл обновится сам.

| Где стоит скилл | Как до людей доходит обновление |
|---|---|
| claude.ai по ссылке (Desktop, Code, web) | само, после перезаливки |
| репозиторий (Claude Code, Codex) | после `git pull` |
| ChatGPT / свой загруженный `.skill` | никак: копию нужно перезагрузить вручную |
