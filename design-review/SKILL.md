# Дизайн-ревью: сборка ↔ макет

Инструмент дизайнера для приёмки дизайна. Задача — снять с человека механическую сверку и оставить ему только суждение.

**Принцип:** машина закрывает 13 из 16 критериев регламента полностью — все «Значимые» и «Незначительные». Дизайнер выходит на ревью только с тем, где он незаменим: сценарии, логика, восприятие, потеря данных.

**Среда.** Скилл работает в Claude (Code / Desktop / claude.ai), OpenAI Codex и ChatGPT. Ниже действия названы по смыслу («открыть страницу», «выполнить JS»). Конкретные имена инструментов в каждой среде — в `references/tools.md`, прочитай его в начале прогона. Перед стартом определи, что доступно:

| Возможность | Если есть | Если нет |
|---|---|---|
| Figma MCP | эталон из Figma (раздел 1) | попроси скрины макета + значения токенов; точность ниже |
| Браузер с выполнением JS | вариант А (раздел 2) | вариант Б — по скринам/видео |
| Запись в Figma | шаблон в Figma (раздел 5А) | документ (раздел 5Б) |

Чего не хватает — скажи пользователю в начале одной строкой, а не в конце.

## 0. Что нужно на входе

Проверь наличие. Чего нет — спроси **одним сообщением**, не по одному:

| Обязательно | Формат |
|---|---|
| Эталон | ссылка на фрейм Figma с `node-id` (**не** на файл целиком) **и/или** эталон в репозитории: прототип, спецификация (раздел 1б) |
| Сборка | URL стенда · локальная сборка разработчика (`localhost`) · ветка/PR с инструкцией запуска · скрины/видео (раздел 2) |
| Что осознанно не вошло | список — иначе будут ложные замечания |

Опционально: доступы/тестовые учётки, целевые вьюпорты, приоритетные браузеры (по аналитике), режим (первичное / повторное), **кто запускает** (дизайнер на приёмке / разработчик на самопроверке, раздел 5В), что под вопросом (→ блок «Уточнить»).

Если макет дан ссылкой на файл без `node-id` — попроси ссылку на конкретный фрейм. Без этого сравнивать не с чем.

**Если в репозитории есть инструкция к ревью** (например `design-review/DEV_SELF_REVIEW.md`, `DESIGN_FIGMA.md`, `CORNER_CASES.md`) — прочитай её первой: там ссылки на макеты, эталон, что не вошло и готовый запрос. Не переспрашивай то, что в ней уже есть.

## 1. Снять эталон из Figma

Порядок обязателен, не пропускай:

1. **`get_metadata`** по корневому узлу → дерево нод (ID, имена, типы, координаты, размеры). Это карта — по ней ориентируешься дальше, не выжигая контекст.
2. **`get_design_context`** по целевым нодам → свойства, структура, референсный код. Если ответ обрезан — вернись к `get_metadata`, разбей на части, запроси заново.
3. **`get_variable_defs`** → токены цветов, отступов, типографики. **Критично:** дальше сравнивай в токенах, а не в px. Это единственный способ пережить разницу вьюпортов и закрыть п.6 регламента («использованы ли токены из библиотеки, а не локальные копии и хардкод»).
4. **`get_screenshot`** по каждому фрейму → эталонная картинка для визуальной сверки и для шаблона.

Собери эталон в таблицу: нода → ожидаемые свойства → токен. Это база сравнения.

---

## 1б. Эталон из репозитория

Не всё есть в Figma: выпадашки, состояния, анимации, корнер-кейсы часто живут только в прототипе или в спецификации. Тогда эталон — репозиторий.

**Что искать в репе:**
- **прототип** (HTML/JS, Storybook, React-песочница) — эталон для того, чего нет фреймом в макете;
- **спецификация** — описание макета со ссылками на ноды (`DESIGN_FIGMA.md` и т.п.), корнер-кейсы (`CORNER_CASES.md`), README;
- **токены/кит** — файлы токенов, компоненты кита, Code Connect: ожидаемые размеры, варианты (`size="L"`), имена токенов.

**Как снять эталон с прототипа:**
1. Если репо удалённое — склонируй во временную папку (не в рабочую папку пользователя). Gitea/GitLab в браузере показывают исходники, а не страницу — прототип нужно запустить.
2. Запусти так, как написано в README/инструкции; для статического HTML — `python3 -m http.server <порт>` из корня. **Не открывай через `file://`** — не загрузятся иконки, шрифты, данные.
3. Выставь то же состояние, что на сборке (query-параметры, выбранные фильтры, регион).
4. Сними данные **тем же JS-шаблоном**, что и сборку (раздел 2А). Прототип ↔ сборка — это DOM ↔ DOM, сравнение точное, без догадок.

**Приоритет источников при расхождении:** Figma-фрейм > спецификация > прототип. Если прототип противоречит макету — не выбирай сам, вынеси в «Уточнить». В отчёте у каждого замечания укажи, откуда эталон: «Макет (нода …)» или «Прототип (`tooltip_price`)».

## 2. Снять сборку

Сборка может прийти в разном виде:

| Что прислали | Что делать |
|---|---|
| URL стенда / превью-окружения | вариант А |
| локальная сборка разработчика (`localhost:…`) | вариант А — открывается только на машине, где запущена; если запускает сам разработчик — это самопроверка (5В) |
| ветка / PR / коммит | попроси ссылку на превью-стенд; если его нет — запусти по README проекта во временной папке и дальше вариант А. Не меняй код и не пушь |
| скрины / видео | вариант Б |

Для стенда за VPN/авторизацией — браузер должен быть уже залогинен; если страница не открывается, скажи об этом сразу, не гадай по исходникам.

### Вариант А — есть живая сборка (предпочтительно)

**Открыть страницу** → стенд. Дальше по каждому состоянию из матрицы (раздел 6):

- **изменить размер окна / вьюпорт** — прогон по вьюпортам
- **скриншот** — визуальная фиксация
- **дерево доступности** (accessibility snapshot) — роли, фокус, имена элементов
- **выполнить JS на странице** — **главный источник фактов.** Снимай `getComputedStyle` по элементам, соответствующим нодам Figma:

```js
// шаблон съёма
[...document.querySelectorAll(SEL)].map(el => {
  const s = getComputedStyle(el), r = el.getBoundingClientRect();
  return {
    sel: SEL,
    box: {x: r.x, y: r.y, w: r.width, h: r.height},
    font: [s.fontFamily, s.fontSize, s.fontWeight, s.lineHeight, s.letterSpacing],
    color: [s.color, s.backgroundColor, s.borderColor],
    space: [s.paddingTop, s.paddingRight, s.paddingBottom, s.paddingLeft, s.gap],
    radius: s.borderRadius,
    text: el.textContent.trim()
  };
})
```

Дополнительно через выполнение JS:
- битые картинки: `[...document.images].filter(i => !i.complete || i.naturalWidth === 0)`
- пикселизация: `naturalWidth` против `clientWidth * devicePixelRatio`
- «скачки» интерфейса: `PerformanceObserver` на `layout-shift`
- неразрывные пробелы: поиск `\u00A0` в текстовых узлах

### Вариант Б — скрины или видео от пользователя

Из видео бери только кадры, где интерфейс устоялся (после окончания анимации), а не каждый. Каждый устоявшийся кадр дальше = обычный скриншот. Отдельно отмечай то, что видно только в динамике: дёрганые переходы, скачки лейаута, внезапный скролл.

**Ограничение — озвучь его пользователю:** без доступа к DOM точность по отступам и типографике падает. Замечания этого класса помечай `confidence: low` и формулируй как «похоже на», а не как факт.

## 3. Сравнить — тремя слоями, в этом порядке

**Слой 1 — детерминированный (основа).** Свойства Figma ↔ computed styles. Даёт точные формулировки: «padding-top 24px вместо 32px (токен `space/xl`)». Ноль догадок. Максимум находок отсюда.

**Слой 2 — визуальный.** Сравнение скриншота с `get_screenshot`. Ловит то, чего нет в DOM: иконки, тени, обрезка. **Много ложных срабатываний — используй только чтобы указать зоны для слоя 3, не как источник замечаний.**

**Слой 3 — визуальный анализ по зонам.** Только по подозрительным областям из слоя 2, не по экрану целиком. Для неформализуемого: баланс, переполнение текста, несогласованность состояний. **Не проси себя измерять пиксели — только классифицируй и формулируй.**

### Нормализация — обязательна

- Сравнивай **токены и относительные величины**, не абсолютные px. Макет 1440, окно 1394 — абсолюты бессмысленны.
- Проверь `devicePixelRatio`. DPR 2 против 1 ломает все пороги.
- Текст сравнивай **семантически**. В макете плейсхолдер, в сборке реальные данные — это не баг. Баг — когда отличается сама строка интерфейса (лейбл, кнопка, ошибка).
- Всё из «осознанно не вошло» — отфильтруй до классификации.

## 3б. Чекап компонентов дизайн-системы — обязателен

Каждое ревью проверяет не только «похоже ли», но и **из чего собрано**: компоненты и токены ДС или локальные копии и хардкод. Это п.6 регламента. Не пропускай, даже если визуально всё совпало.

**1. Что ожидается — из макета.**
- По `get_metadata` / `get_design_context` выпиши все **инстансы библиотечных компонентов**: имя компонента, вариант и свойства (`Size=L`, `State=Active`, `Type=Secondary`).
- `get_code_connect_map` — какой компонент в коде соответствует компоненту Figma и с какими пропсами. Если маппинга нет — `search_design_system` / `get_libraries`, чтобы найти компонент кита по имени.
- Заодно проверь **сам макет**: detached-инстансы, локальные стили и цвета вне токенов. Это не замечание к разработчику — вынеси в «Уточнить» для дизайнера.

**2. Что использовано — в сборке.**
- **DOM:** признаки компонентов кита — классы с префиксом кита, `data-*`-атрибуты, `data-testid`, имена компонентов. Через JS собери: элемент → вероятный компонент → вариант (по размеру, классу-модификатору).
- **Код** (если есть доступ к репозиторию сборки или PR): импорты из пакета ДС и пропсы (`size="XS"` вместо `"L"`), самописные компоненты на месте китовых, значения стилей не через токены (`#d0d8e9`, `padding: 12px` вместо переменной).
- **Токены:** сопоставь computed-значения с `get_variable_defs`. Значение совпадает с токеном по цифре, но в коде захардкожено — это тоже находка.

**3. Сведи в таблицу «Компоненты ДС»** — отдельный блок отчёта:

| Элемент | В макете | В сборке | Статус |
|---|---|---|---|
| Чипс фильтра | `Filters / Chip`, Size=L | кнопка кита, size XS | ⚠️ другой вариант |
| Выпадашка цены | `tooltip_price` | старый поповер | ❌ не тот компонент |
| Поле «от/до» | `Input`, Size=M | `Input`, M | ✅ |

Статусы: ✅ компонент и вариант совпадают · ⚠️ компонент тот, вариант/пропсы другие · ❌ свой компонент, старый компонент или копия вместо китового · 🎨 хардкод вместо токена · ❓ не удалось определить (нет доступа к коду, нет признаков в DOM) — так и пиши, не угадывай.

**Классы:** ⚠️ и ❌ с видимым отличием — по обычным правилам (обычно Критичное: состояния, наполнение не по макету). ❌ и 🎨 **без** видимого отличия — Значимое: сейчас не видно, но разъедется при следующем изменении ДС. Без доступа к коду 🎨 не утверждай — только «похоже на хардкод».

Повторяющиеся ⚠️/❌ — прямой кандидат в «В базу типовых ошибок» с профилактикой через Code Connect (прописать вариант по умолчанию, связать компонент).

## 4. Классифицировать — по регламенту команды

Каждому замечанию сразу проставляется класс. Это снимает споры о том, что чинить до релиза.

### Критичные — блокируют или заметно ломают восприятие · до релиза
- работоспособность сценария, тупиковые пути, необработанные ошибки, неверное поведение контролов
- наполнение экрана не по макету — влияет на восприятие и узнаваемость бренда
- нарушение сетки
- тексты не по макету
- состояния элементов и их стили при смене состояния
- заметная пикселизация, битые картинки
- **сильно поехавшие отступы** → порог: отклонение **≥ 8px или ≥ 25%**
- потеря или искажение данных пользователя

### Значимые — не блокируют, но ухудшают качество · до релиза
- типографика: шрифт, размер, вес, line-height, letter-spacing
- отображение на разных разрешениях
- контрастность и доступность на основном пути

### Незначительные — после релиза или по договорённости
- размер иллюстраций и иконок
- отсутствие неразрывных пробелов
- **небольшое несоответствие отступов** → отклонение **< 8px и < 25%**
- отображение в разных браузерах
- адаптивность на планшете

Пороги по отступам вынеси в начало отчёта явно, чтобы команда могла их откалибровать после первых прогонов.

### Отдельно
- **Рефакторинг.** Если правка тянет заметный рефакторинг — не «протаскивай» через ревью. Помечай `→ отдельная задача с приоритизацией`.
- **Логика.** Баги логики не смешивай с UI. Отдельный блок с пометкой «сверить с QA на дубли», путь воспроизведения, модель/ОС, ожидаемая реализация.
- **Уточнить.** Расхождение есть, но неясно, входит ли это в итерацию (пункт «под вопросом», макет противоречит прототипу, нет фрейма на состояние). Не классифицируй — отдельный блок «Уточнить у команды» и отдельная колонка в счётчике.

## 5. Оформить результат

Спроси, если не указано: **шаблон в Figma** или **документ**. По регламенту UI-правки идут одной задачей со ссылкой на шаблон — Figma по умолчанию.

### Вариант А — шаблон ревью в Figma

**Перед любым вызовом `use_figma` загрузи скилл `figma-use`** (в Claude — из плагина Figma; в других средах — `skill://figma/figma-use/SKILL.md` через MCP-ресурсы Figma, если клиент их читает). Без этого будут труднодиагностируемые сбои. Если `use_figma` в среде недоступен — переходи к варианту Б и скажи об этом.

Строй фрейм в формате «как в сборке» / «как нужно»:
- слева скриншот сборки с подсветкой проблемных зон, справа эталон
- каждое замечание — пронумерованный маркер + комментарий: что не так, ожидаемый результат, класс критичности
- группировка по классам, Критичные сверху
- у каждого замечания статус-компонент «Не исправлено» / «Исправлено»
- в шапке: ссылка на задачу, дата, вьюпорты, пороги, счётчик по классам

### Вариант Б — документ

Markdown-файл той же структуры: шапка → сводка по классам → замечания с превью, ожидаемым результатом и ссылкой на ноду.

- **Шапка:** сборка (ссылка), эталон (ноды Figma + прототип/спека из репо), режим, что вне ревью, условия (браузер, DPR, ширина окна), пороги.
- **Счётчик:** Критичные · Значимые · Незначительные · Уточнить.
- **Замечание:** таблица «Сборка / Макет (или Прототип)» по свойствам + скрины рядом.
- **Компоненты ДС:** таблица из раздела 3б со статусами ✅ ⚠️ ❌ 🎨 ❓.
- **В конце:** таблица «Проверено / Не проверено» и блок «В базу типовых ошибок».
- **Куда сохранять** (если работаешь в репозитории): `design-review/<ГГГГ-ММ-ДД>/REVIEW.md`, скрины рядом (`build-*.png`, `figma-*.png`, `proto-*.png`). Эта папка — вход для повторного ревью.

### Вариант В — самопроверка разработчика

Если скилл запускает разработчик на своей сборке до передачи на ревью:
- результат — **черновик к приёмке, не приёмка**; так и подпиши в шапке;
- Критичные и Значимые — исправить до передачи; «Уточнить» — не чинить, принести дизайнеру;
- замечание кажется ложным (реальные данные, сознательное отступление) — **не удалять**, оставить с комментарием; решает дизайнер;
- сценарии, логику и восприятие не оценивай — это делает дизайнер на приёмке.

Дизайнер может подготовить для разработчика инструкцию в репо (`design-review/DEV_SELF_REVIEW.md`): установка, ссылки на эталон, что не вошло, готовый запрос, как читать результат. Если попросили её сделать — бери эту структуру.

### Во всех случаях — сводка для Slack

Коротко, без стены текста: счётчик по классам и «Уточнить», ссылка на шаблон/отчёт, явный флаг если много мелких («подсветить разработчику на старте, чтобы он ещё раз внимательно посмотрел макеты»).

---

## 6. Матрица прогона — чек-лист состояний

Проверяй каждое. Пропущенное — отметь как непроверенное, не молчи.

**Данные:** загрузка (что скрыто, что показано) · пустое состояние · много данных · мало данных · перекрытие важной информации · длинные тексты (переполнение, обрезка, перенос, локализация)

**Ошибки:** валидация · системная ошибка · отсутствие интернета

**Контролы:** hover · pressed · focus · disabled · поиск (ввод, успех, неуспех)

**Навигация:** прокрутка · пагинация · анимации и эффекты при взаимодействии

**Адаптив:** горизонтальная и вертикальная ориентация · разные разрешения · браузеры по аналитике · планшет

**Система:** тёмная/светлая тема · увеличенный системный шрифт · safe areas и вырезы экрана · клавиатура (перекрытие полей, скролл под ней)

**Качество загрузки:** скелетоны, зарезервировано ли место под контент, скачки интерфейса

**Доступность:** контраст · размеры тап-зон · фокус при навигации с клавиатуры

## 7. Повторное ревью

Если это второй заход — запроси предыдущий отчёт или шаблон.

1. Считай **fingerprint** каждого замечания: `хеш(класс + имя ноды в Figma + свойство + нормализованный селектор)`. **Не координаты** — они плывут, и одна и та же ошибка расползётся на десяток дубликатов.
2. Сопоставь с прошлым прогоном:
   - исчезло → статус «Исправлено», дизайнер только подтверждает
   - осталось → «Не исправлено», поднять в списке
   - новое → пометить как регрессию, это важный сигнал
3. В сводке: сколько исправлено, сколько осталось, сколько новых.

**Лимит — две полные итерации.** Если после второй остаются Критичные, не начинай третий круг — вынеси это отдельным пунктом: повод для разбора причин с командой.

---

## 8. Завершение

Ревью закрыто, когда:
- Критичные и Значимые исправлены и подтверждены на повторном ревью
- Незначительные заведены в бэклог с меткой `design-debt` и сроком — иначе теряются
- у всех замечаний финальный статус: «Исправлено» / «Отложено»

Закрытие задачи DESIGN REVIEW = сигнал «дизайн принят».

---

## 9. Накопление — не пропускай

В конце каждого прогона выведи блок **«В базу типовых ошибок»**: замечания, которые повторяются между прогонами или между экранами.

Для каждого предложи, чем закрыть навсегда: правило линтера, поправка в UI-кит, дизайн-токен, запись в гайдлайн, Code Connect. Профилактика дешевле ревью — короткий walkthrough макетов с разработчиком до старта разработки снимает большую часть замечаний.

---

## Что не делай

- Не измеряй пиксели «на глаз» по скриншоту — только через DOM или с явной пометкой низкой уверенности
- Не выдавай замечание там, где расхождение объясняется реальными данными вместо плейсхолдера
- Не смешивай UI и логику в одном списке
- Не выдавай длинный список без классов критичности — он бесполезен
- Не пропускай состояния из матрицы молча
- Не пропускай чекап компонентов ДС (3б), даже если визуально всё совпало
- Лучше 5 точных замечаний, чем 30 с мусором. Ниже ~70% подтверждаемости инструментом перестают пользоваться.
